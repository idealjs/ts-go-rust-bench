# 性能差距核心代码原因报告（root-cause analysis, 2026-09-04）

配套 `2026-09-04.md`（首测数据）。本报告回答：**31× 中位差 / 60-208× 热点差的差距在代码里的哪里。**

## 方法

perf 被禁（paranoid=4）、valgrind 不可用、gdb 批处理采样不可行；改用 env 门控相位探针
（`TSOX_PROBE_T0`/`TSOX_PROBE_PARSE`，测后已从工作区剥离，未入库）对
release 构建做逐段计时，再对单文件解析做独立微基准（`cargo test --lib`，已剥离）。

## 底板分解：每次程序构建的 1.1-1.6s 花在哪

以 `01-startup-floor/2dArrays`（236B 源文件）为基准（多轮取值波动 ±20%）：

| 阶段 | 耗时 | 占比 |
|---|---|---|
| **默认库解析**（19 个 lib .d.ts，2.68MB） | **0.96–1.40s** | **~90%** |
| 模块解析 | 2ms | <0.2% |
| 绑定（108+20 文件全部 bind） | 23ms | ~1.5% |
| 语义检查（含库） | 0.13–0.16s | ~10% |
| worker 启动+用例解析 | 0.3–0.5s | （进程外） |

结论一：**差距的主体是解析器，不是类型检查器。** 绑定、模块解析、检查内核
全部在几十毫秒级。

## 解析器：数字与病灶

- 整库集吞吐 **2.67 MB/s**；逐文件（release，独立微基准）：
  - `lib.dom.d.ts` **2.35MB → 1.353s（1.7 MB/s）** ← 单文件占整底板 ~70%
  - `lib.es5.d.ts` 219KB → 18.8ms（**11.6 MB/s**）——同一解析器的内容依赖病态
- Go 对照：tsgo 全流程（解析同一 2.7MB 库图 + 绑定 + 检查）42ms（--skipLibCheck，
  语料研究）/ 164-265ms（无 skipLibCheck，bench 口径）→ **解析吞吐差 ~30-40×**。

### dom.d.ts 病灶分离（独立微基准）

| 变体 | 字节 | 解析 |
|---|---|---|
| dom 原文 | 2.35MB | 1.353s |
| dom 去注释 | 0.79MB（**66% 是注释**） | 0.360s |

- **注释扫描 ≈ 1.0s（占 dom 解析 75%）**，注释字节速率 0.64 MB/s，比代码还慢 3.4×
  ——扫描器的注释/空白路径存在逐字符慢路径（疑似逐字符 push/UTF-8 分发，无批量跳过）。
- 去注释后仍只有 2.2 MB/s（es5 全文 11.6MB/s 的 1/5）：接口/泛型密集的"纯代码"部分
  也有 ~5× 的结构开销（每节点 Arc 分配、text() String 化、无标识符 interning 量级）。

## 多配置放大器：头条热点差的直接来源

官方用例普遍带 2-24 个配置（`@target: a,b` / `@module: …` 矩阵）；**每个配置完整
重建程序（重复解析全部库）**。实测线性拟合：

| 用例 | 配置数 | 墙钟 | 每配置 |
|---|---|---|---|
| commentsOnJSXExpressionsArePreserved | **24** | 12.8s | 0.53s |
| moduleResolutionWithModule | 10 | 10.7s | 1.07s |
| numericUnderscoredSeparator | 7 | 6.8s | 0.97s |
| bundlerDirectoryModule | 6 | 6.5s | 1.08s |
| jsxEmptyExpressionNotCountedAsChild | 3 | 3.5s | 1.16s |

→ bench 里 60-208× 的"JSX/模块解析热点"**没有 JSX 或解析专属病理**，
全部等于 `配置数 × 固定底板`。Go 侧同用例 30-45ms（其底板小 30×，配置数一样多）。

## 检查器内核：健康

- 热点家族语义检查 0.13-0.16s（对 Go 的同段不可比但绝对值小）。
- `relationComplexityError`（Go 全程 1.44s，其时间几乎全在关系引擎）我们仅 **0.13s**
  ——该族 Rust 内核反而快 ~10×，差距全是底板。

## 已排除（非当前瓶颈）

模块解析（2ms）、绑定（23ms）、诊断渲染、JSX 检查路径本身、node_modules 走查
（bundlerDirectory 的 6.5s 同样是 6×底板）。

## 修复优先级（按预期收益）

1. **跨配置复用已解析库**（harness/program 层，不改内核）：24 配置用例 12.8s → ~1.6s；
   全库墙钟估计 -55%（sweep 实测多配置族占大头）。
2. **扫描器注释/空白批量跳过 + ASCII 快路径**：dom 1.35s → 预计 ~0.4s；底板 -60%。
3. **解析器分配架构**（节点 arena、标识符 interning、text 零拷贝）：去注释后仍有
   ~5× 结构开销可收。
4. 完成后用 `bench/compare.py` 重测——这正是本仓库存在的目的。
